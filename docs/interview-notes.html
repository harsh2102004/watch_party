Project Overview

The Watch Party application is a synchronized video watching platform that lets friends watch videos simultaneously across different devices and locations with real-time video playback synchronization, live role permissions (Host, Moderator, Participant, Viewer), and room lifecycle management.

It is built as an npm monorepo with an Express and Socket.IO backend in /server and a React Vite frontend in /client. State is kept authoritative on the server using extrapolated mathematical timestamps so that late-joining participants and users with slight network lag always stay locked to the exact same second of video without requiring constant spam of network packets.

Subtask 5.6: MongoDB Persistence with Mongoose, TTL Pruning & Non-Blocking Resilience Database & Persistence

1. What We Built

A resilient MongoDB persistence architecture using Mongoose that strictly separates live in-memory state from persistent storage:

  • Non-Blocking Connection Engine (connect.js): Connects asynchronously to MongoDB via process.env.MONGODB_URI without blocking server startup. Implements exponential backoff retries (2s–30s) and exports isDbConnected() based on mongoose.connection.readyState === 1. If MONGODB_URI is absent or unreachable, logs a clear warning and seamlessly runs in pure memory-only mode.
  • Mongoose Schemas with 7-Day TTL (RoomDoc & Message):
    • RoomDoc: Stores roomId (unique, indexed), videoId, createdAt, and lastActiveAt with a 7-day TTL index (index: { expires: '7d' }). Named RoomDoc to prevent collision with the in-memory Room class.
    • Message: Stores roomId, userId, username, text (max 300 chars), and timestamp with a compound index { roomId: 1, timestamp: 1 } and a 7-day TTL index.
  • Fault-Tolerant Repository (RoomRepository.js): Provides saveRoom, updateVideo, touchRoom, findRoom, saveMessage, and getRecentMessages(limit = 50). All writes are fire-and-forget (void), never awaited in socket handlers, wrap operations in try/catch, enforce maxTimeMS: 3000 timeouts, and return null / [] immediately when disconnected.
  • Restoration on Join: When a user emits join_room for a room not present in memory, the server checks findRoom. If found in MongoDB, the room is reconstituted in RoomManager (paused at time 0), recent messages are loaded into the chat cache, and the first joiner is designated as Role.HOST.
  • Health Check API: Extended GET /health to report { status: "ok", db: "connected" | "disconnected" | "disabled" }.

4. Key Decisions & Why

  • Why keep live state in-memory and only persist metadata to MongoDB? High-frequency video sync (sub-second seek calculations, playback toggles) requires zero latency ($< 1\text{ ms}$). Round-tripping ephemeral play state to a remote database introduces 50–200ms network lag and write bottlenecks. The in-memory Room class remains the authoritative source of truth, while MongoDB stores only restart-surviving state.
  • Why fire-and-forget writes? A slow database write or network hiccup must never stall a user's WebSocket message. By not awaiting write operations inside event handlers, real-time broadcasts continue without pause.
  • Why maxTimeMS: 3000? If MongoDB experiences heavy load, operations fail fast after 3 seconds instead of hanging promises indefinitely and leaking server memory.
  • Why 7-day TTL indexes? Rooms and chat logs for ephemeral watch parties have finite lifetimes. Leveraging MongoDB's background TTL index thread automates garbage collection without external cron workers.

5. Alternatives Considered

  • Alternative: Awaiting database writes in socket handlers: Guarantees write confirmation before broadcasting, but ties WebSocket responsiveness directly to database latency. A database slowdown would freeze video controls and chat for all connected users.
  • Alternative: Restoring all rooms at boot: Scanning and restoring thousands of dormant rooms at server startup consumes unneeded RAM. Lazy restoration on join_room restores only rooms that users actually visit.

6. Problems Encountered & Fixes

  • Problem: Database failure crashing socket handlers: Uncaught promise rejections in Mongoose queries could crash the Node.js process. Fix: All repository write calls chain .catch() to log warnings, and findRoom / getRecentMessages wrap operations in try/catch returning safe fallback values (null or []).

7. Expected Interview Questions & Answers

Q1: How does your architecture ensure that a database outage never impacts active watch party participants?
All live synchronized playback states, participant rosters, and role permissions reside strictly in the server's in-memory Room and Participant models. Repository methods check isDbConnected() first; if disconnected, they return immediately. All write calls are fire-and-forget, and read calls are wrapped in try/catch with 3-second timeouts. If MongoDB goes down completely, the server seamlessly continues operating in memory-only mode without dropping sockets or throwing errors.
Q2: Why use a 7-day TTL index on lastActiveAt instead of a manual cleanup job?
MongoDB's TTL (Time-To-Live) index automatically runs a background task once every 60 seconds to prune documents whose timestamp has passed the expiration threshold. This eliminates the need for separate worker cron jobs or custom scheduled scripts, ensuring automated, zero-maintenance pruning of inactive rooms and stale chat messages.
Q3: What happens when a user joins a room that was persisted in MongoDB after a server restart?
When join_room is emitted for a room not currently in memory, the handler queries roomRepository.findRoom(roomId). If a document exists, the room is reconstituted in RoomManager with its saved videoId, paused at time 0, and populated with its last 50 chat messages via getRecentMessages(). Because the room is currently empty, the incoming joiner is promoted to Role.HOST, granting them immediate control over playback.

Subtask 5.7: User Authentication, Socket Handshake Auth, Reconnect Role Restoration & React Client Auth UI Security & Identity

1. What We Built

A hybrid JWT + Socket.IO authentication and identity system supporting registered user accounts, guest access, session reconnects, and single-session enforcement across tabs:

  • Mongoose User Model & Auth Routes: User schema with unique lowercase email, unique 3-20 char username, and passwordHash. Express endpoints POST /auth/register, POST /auth/login, GET /auth/me, and GET /auth/config. Passwords hashed with bcrypt (cost 10); JWT tokens signed with JWT_SECRET (7-day expiry). express-rate-limit protects auth routes against brute-force attacks.
  • Socket.IO Authentication Middleware (io.use): Extracts token from socket.handshake.auth.token, verifies signature, and attaches identity to socket.data.user = { userId, username }. If token is missing, falls back to guest identity if ALLOW_GUESTS=true; otherwise rejects connection with UNAUTHORIZED. In create_room and join_room, identity is sourced from verified socket.data.user rather than client-supplied inputs.
  • Seamless Reconnection & Role Restoration: When an authenticated user refreshes the page or suffers a momentary network disconnection, the server preserves and restores their existing participant entry and role (e.g. HOST or MODERATOR) rather than rejecting with duplicate username or resetting privileges.
  • Single-Session Multi-Tab Replacement: If an authenticated user opens a second browser tab to the same room, the server detects the active session, disconnects the older socket with a session_replaced event, and mounts the new tab cleanly.
  • React Client Auth Architecture:
    • AuthProvider.jsx: Exposes user, token, login, register, logout, continueAsGuest, and dispatches custom window events (auth:login, auth:logout) so SocketProvider immediately reconnects with the fresh token.
    • ProtectedRoute.jsx: Guards application routes, redirecting unauthenticated visitors to /login while preserving destination in location.state.from.
    • Login.jsx and Register.jsx: Clean form validation, error banners, and "Continue as Guest" entry points.
    • UserNav.jsx: Displays active user pill and sign out / logout controls.
    • Adaptive Landing & Room forms: Logged-in users see "Creating/Joining as username" without redundant name input fields.

  1. Socket Handshake Auth:

4. Key Decisions & Why

  • Why localStorage for JWT in this architecture? WebSockets require attaching the token to socket.handshake.auth.token during connection initiation. HttpOnly cookies cannot be read by JavaScript to populate custom handshake objects and introduce complex SameSite/CORS cookie negotiation across separate origins (e.g. Vercel frontend, Render backend).
  • Why replace the older tab socket rather than reject the new tab? In real-world browser usage, users often duplicate a tab, refresh a stuck window, or click an invite link while already having a window open. Rejecting the new tab forces a frustrating deadlock; kicking the older tab with an explicit notice mirrors Google Docs and Slack behavior.
  • Why restore roles on reconnect? If a network drop or page refresh caused a room host to be demoted or rejected with USERNAME_TAKEN, meeting moderation would break constantly. Linking identity to userId guarantees seamless session persistence.

5. Alternatives Considered

  • Alternative: HttpOnly Cookies with Cookie-based Handshake: Provides immunity to token exfiltration via XSS, but breaks cross-site third-party cookie policies in modern browsers when frontend and backend reside on different domains (e.g. .vercel.app and .onrender.com).
  • Alternative: Ephemeral Guest-only System: Easiest to implement, but users cannot reclaim room leadership or preserve their identity across device reboots.

6. Problems Encountered & Fixes

  • Problem: Socket handshakes failing when switching between Guest and Logged-in: The socket client instance did not dynamically update its handshake auth payload. Fix: Implemented custom window events (auth:login, auth:logout) that signal SocketProvider to update socket.auth and invoke socket.disconnect().connect().

7. Expected Interview Questions & Answers

Q1: What are the security trade-offs of storing JWTs in localStorage versus httpOnly cookies?
Storing JWTs in localStorage leaves them vulnerable to exfiltration if the application suffers a Cross-Site Scripting (XSS) flaw. However, localStorage is immune to Cross-Site Request Forgery (CSRF) since tokens must be explicitly attached via code. Furthermore, for decoupled architectures where client (Vercel) and API/WebSockets (Render) live on different parent domains, localStorage eliminates SameSite cross-origin cookie restrictions and allows direct transmission in the Socket.IO handshake auth dictionary.
Q2: How does your server prevent two browser tabs from having conflicting control over the same room?
When an authenticated user connects and enters a room, the server checks whether their unique userId already has an active participant record with a differing socketId. If detected, the server emits a session_replaced notification to the older socket and forces its disconnection, then transfers the existing role (such as HOST) to the new socket connection.
Q3: How does the system handle database outages during authentication?
If MongoDB is disconnected or disabled, registration and login endpoints return a clean 503 Service Unavailable with an explanatory message ("Authentication service unavailable in memory-only mode"). If ALLOW_GUESTS=true, users can continue directly into watch parties as guests, ensuring zero disruption to playback synchronization.

4. Key Decisions & Why

  • Why bind to 0.0.0.0 instead of localhost? In containerized platforms like Render and Docker, binding to localhost listens only on the container's private loopback interface. 0.0.0.0 instructs the OS to accept incoming traffic routed through the public container proxy.
  • Why probe /health via REST before connecting the socket? Render free-tier cold starts take 30–60 seconds. Initiating raw WebSocket handshakes during spin-up leads to rapid connection retry exhaustion and degraded UX. Probing /health first keeps the user informed with live progress.
  • Why allow both websocket and polling transports? Some corporate firewalls and mobile proxies block WebSocket upgrade handshakes (HTTP 101). Socket.IO's dual transport configuration falls back gracefully to HTTP long-polling when WebSockets are obstructed.

5. Alternatives Considered

  • Alternative: Monolithic Single-Server Deployment: Serving the client static build directly from Express avoids CORS entirely. However, hosting on Vercel leverages its global Edge CDN, instant preview deployments for PRs, and leaves the Node server dedicated entirely to real-time WebSocket compute.
  • Alternative: Wildcard CORS (*): Disallows credentials: true and exposes private watch party endpoints to malicious third-party websites. Explicit origin whitelisting ensures robust cross-origin security.

6. Problems Encountered & Fixes

  • Problem: Vercel preview deployments failing CORS: Each pull request generates a unique dynamic URL (e.g. watch-party-abc-username.vercel.app) that cannot be hardcoded in CLIENT_URL. Fix: Added ALLOW_VERCEL_PREVIEWS=true which dynamically matches any secure origin ending in .vercel.app.

7. Expected Interview Questions & Answers

Q1: How does your application mitigate the user experience friction of Render's free-tier container sleep?
On initial load, the client executes a health check against GET /health with cache: 'no-store'. If the server is sleeping, the application mounts a dedicated ColdStartScreen with an animated spinner and a real-time elapsed seconds counter, clearly explaining that the cloud server is waking up. The hook polls every 3 seconds up to 90 seconds, and transitions smoothly into the watch party lobby as soon as the server responds.
Q2: Why is multi-origin CORS required for Socket.IO when splitting frontend and backend deployments?
Socket.IO begins with an HTTP handshake containing an Origin header sent by the browser. If the client runs on my-watch-party.vercel.app and the backend runs on onrender.com, the browser enforces Cross-Origin Resource Sharing. Because we allow authentication credentials (credentials: true), Socket.IO forbids wildcard (*) origins. Our utility parses a comma-separated list of allowed origins and supports regex matching for dynamic Vercel PR preview branches.
Q3: What occurs during graceful shutdown on Render?
When Render redeploys or restarts a container, it dispatches a SIGTERM signal. The server captures this signal, immediately stops accepting new HTTP connections via server.close(), closes all active Socket.IO connections, drains and closes the MongoDB Mongoose connection pool, and clears room sweep timers. A 10-second timeout guarantees that if any socket hangs during closure, the process terminates with process.exit(1).

  • Why fire-and-forget writes? A slow database write or network hiccup must never stall a user's WebSocket message. By not awaiting write operations inside event handlers, real-time broadcasts continue without pause.
  • Why maxTimeMS: 3000? If MongoDB experiences heavy load, operations fail fast after 3 seconds instead of hanging promises indefinitely and leaking server memory.
  • Why 7-day TTL indexes? Rooms and chat logs for ephemeral watch parties have finite lifetimes. Leveraging MongoDB's background TTL index thread automates garbage collection without external cron workers.

5. Alternatives Considered

  • Alternative: Awaiting database writes in socket handlers: Guarantees write confirmation before broadcasting, but ties WebSocket responsiveness directly to database latency. A database slowdown would freeze video controls and chat for all connected users.
  • Alternative: Restoring all rooms at boot: Scanning and restoring thousands of dormant rooms at server startup consumes unneeded RAM. Lazy restoration on join_room restores only rooms that users actually visit.

6. Problems Encountered & Fixes

  • Problem: Database failure crashing socket handlers: Uncaught promise rejections in Mongoose queries could crash the Node.js process. Fix: All repository write calls chain .catch() to log warnings, and findRoom / getRecentMessages wrap operations in try/catch returning safe fallback values (null or []).

  • Why fire-and-forget writes? A slow database write or network hiccup must never stall a user's WebSocket message. By not awaiting write operations inside event handlers, real-time broadcasts continue without pause.
  • Why maxTimeMS: 3000? If MongoDB experiences heavy load, operations fail fast after 3 seconds instead of hanging promises indefinitely and leaking server memory.
  • Why 7-day TTL indexes? Rooms and chat logs for ephemeral watch parties have finite lifetimes. Leveraging MongoDB's background TTL index thread automates garbage collection without external cron workers.

5. Alternatives Considered

  • Alternative: Awaiting database writes in socket handlers: Guarantees write confirmation before broadcasting, but ties WebSocket responsiveness directly to database latency. A database slowdown would freeze video controls and chat for all connected users.
  • Alternative: Restoring all rooms at boot: Scanning and restoring thousands of dormant rooms at server startup consumes unneeded RAM. Lazy restoration on join_room restores only rooms that users actually visit.

6. Problems Encountered & Fixes

  • Problem: Database failure crashing socket handlers: Uncaught promise rejections in Mongoose queries could crash the Node.js process. Fix: All repository write calls chain .catch() to log warnings, and findRoom / getRecentMessages wrap operations in try/catch returning safe fallback values (null or []).

4. Key Decisions & Why

  • Why 7-day TTL indexes? Rooms and chat logs for ephemeral watch parties have finite lifetimes. Leveraging MongoDB's background TTL index thread automates garbage collection without external cron workers.

Subtask 3.7: Reusable Permission Guard (`withPermission`) Security & Middleware
1. What we built
Created a reusable higher-order function withPermission(action, roomManager, handler) in server/src/handlers/guard.js. It resolves the room and participant by socket ID, enforces room membership (NOT_IN_ROOM) and role-based permissions (FORBIDDEN), and delegates to the event handler with pre-resolved context.
2. Files created or changed
  • server/src/handlers/guard.js (Higher-order permission guard function)
  • server/test/guard.test.js (Unit tests for NOT_IN_ROOM, FORBIDDEN, role checks, and success delegation)

3. How it works
Rather than repeating membership lookups and canPerform calls in every socket event listener, withPermission acts as a higher-order wrapper: 
export function withPermission(action, roomManager, handler) {
  return async (socket, data) => {
    // 1. Resolve room & participant (via data.roomId or scanning rooms)
    let targetRoom = data?.roomId ? roomManager.getRoom(data.roomId) : null;
    let targetParticipant = targetRoom ? targetRoom.getParticipantBySocket(socket.id) : null;

    if (!targetRoom || !targetParticipant) {
      for (const [, r] of roomManager.rooms) {
        const p = r.getParticipantBySocket(socket.id);
        if (p) { targetRoom = r; targetParticipant = p; break; }
      }
    }

    // 2. Enforce room membership
    if (!targetRoom || !targetParticipant) {
      return emitError(socket, 'NOT_IN_ROOM', 'You are not in a room.');
    }

    // 3. Enforce role-based permission via permissions.js
    if (!canPerform(targetParticipant.role, action)) {
      return emitError(socket, 'FORBIDDEN',
        `Role "${targetParticipant.role}" is not allowed to perform action "${action}".`);
    }

    // 4. Delegate with clean context
    return handler({ socket, room: targetRoom, participant: targetParticipant, data });
  };
}
4. Key decisions & WHY
  • Higher-Order Function (Decorator pattern): Socket.IO does not have per-event middleware out of the box like Express does. A higher-order function provides clean, reusable middleware-style protection around any event callback.
  • Context injection into handler: Passes pre-fetched { socket, room, participant, data } directly to the handler, eliminating boilerplate lookup queries in individual control handlers.
  • Prioritizing `data.roomId` with fallback: Provides fast direct map lookup if the client supplies roomId, with fallback search by socket.id for backwards compatibility or minimal payloads.
5. Alternatives not chosen & trade-offs
  • Socket.IO global middleware (io.use): Runs only once during initial handshake or per-packet before event routing, making per-action permission checks clumsy. A per-event guard function is much more granular and descriptive.
  • Inline validation in each handler: Leads to massive code duplication across play, pause, seek, change_video, assign_role, and remove_participant handlers.

const YOUTUBE_ID_REGEX = /^[a-zA-Z0-9_-]{11}$/;

export function extractVideoId(input) {
  if (typeof input !== 'string') return null;
  const trimmed = input.trim();
  if (YOUTUBE_ID_REGEX.test(trimmed)) return trimmed;

  try {
    const url = new URL(/^https?:\/\//i.test(trimmed) ? trimmed : `https://${trimmed}`);
    const host = url.hostname.toLowerCase().replace(/^www\./, '');

    if (host === 'youtu.be') {
      const id = url.pathname.slice(1).split('/')[0];
      return YOUTUBE_ID_REGEX.test(id) ? id : null;
    }
    if (host === 'youtube.com' || host === 'm.youtube.com') {
      let id = null;
      if (url.pathname === '/watch') id = url.searchParams.get('v');
      else if (url.pathname.startsWith('/embed/')) id = url.pathname.split('/')[2];
      else if (url.pathname.startsWith('/shorts/')) id = url.pathname.split('/')[2];
      return id && YOUTUBE_ID_REGEX.test(id) ? id : null;
    }
  } catch {
    return null;
  }
  return null;
}
4. Key decisions & WHY
  • Native URL constructor over giant regex: Parsing full URLs with complex regular expressions is notoriously fragile and vulnerable to ReDoS (Regular Expression Denial of Service). Standard new URL() is fast, safe, and handles protocols, ports, and query parameters cleanly.
  • Strict 11-char regex validation: YouTube video IDs are strictly 11 base64url characters ([a-zA-Z0-9_-]{11}). Validating the extracted candidate prevents passing malicious or truncated tokens to YouTube iframe embeds.
  • Auto-prefixing protocol: Users often paste youtube.com/watch?v=... without https://; prefixing ensures new URL() parses successfully instead of throwing.

  • Third-party npm packages (e.g. get-youtube-id): Unnecessary external dependency risk for 50 lines of clear, maintainable native JavaScript code.
  • Calling the YouTube Data API: Requires API keys, costs quota, and introduces network latency just to parse and validate a URL format.

async #onRemoveParticipant({ socket, room, participant, data }) {
  const targetUserId = data?.userId;
  if (!targetUserId || typeof targetUserId !== 'string') {
    return emitError(socket, 'INVALID_REQUEST', 'userId is required.');
  }
  if (targetUserId === participant.userId) {
    return emitError(socket, 'INVALID_REQUEST', 'Cannot remove yourself.');
  }

  const targetParticipant = room.getParticipant(targetUserId);
  if (!targetParticipant) {
    return emitError(socket, 'USER_NOT_FOUND', 'Target user is not in this room.');
  }

  const reason = typeof data?.reason === 'string' && data.reason.trim()
    ? data.reason.trim()
    : 'Removed by host';

  const targetSocket = this.io.sockets?.sockets?.get?.(targetParticipant.socketId)
    || this.io.of?.('/').sockets?.get?.(targetParticipant.socketId);

  if (targetSocket) {
    targetSocket.emit('removed', { reason });
    await targetSocket.leave(room.roomId);
  }

  room.removeParticipant(targetUserId);

  this.io.to(room.roomId).emit('participant_removed', {
    userId: targetUserId,
    participants: room.getParticipantsList(),
  });
}

  • Prohibiting self-eviction: A host cannot kick themselves via moderation; if a host wishes to depart, they must use leave_room or disconnect, which triggers the proper host auto-promotion pipeline.
  • Fallback to safe execution if socket is disconnected: If a participant's socket disconnected or dropped right before the kick event, the handler still cleanly purges them from the Room model and notifies remaining members without throwing an unhandled rejection.

Subtask 3.16: Pending Playback Requests Lifecycle (`Room.pendingRequests`) State & Request Queue
1. What we built
Extended the Room state model to support collaborative playback requests submitted by non-host participants. Each request is stored as a structured object ({ id, type, payload, requesterId, requesterName, createdAt }). Implemented five lifecycle methods: addRequest, getRequest, removeRequest, getPendingList, and a TTL-based garbage-collection helper cleanExpired(ttlMs).
2. Files created or changed

  • server/test/room.test.js (Added 6 unit tests covering request addition, custom IDs/payloads, invalid type rejection, retrieval, deletion, and TTL expiration)
3. How it works
When non-host participants propose playback actions, the room buffers them in this.pendingRequests (an in-memory Map<string, PendingRequest>):
  1. addRequest(request): Validates that type is one of 'play' | 'pause' | 'seek' | 'change_video' (throwing an error otherwise). Assigns a UUID if id is omitted, sets createdAt to Date.now(), defaults empty payload to {}, stores it in the Map, and returns the request object.
  2. getRequest(id): Performs an O(1) lookup by request ID.
  3. removeRequest(id): Deletes the request from the Map, returning true if found and removed.
  4. getPendingList(): Returns an array of all active pending requests via Array.from(this.pendingRequests.values()).
  5. cleanExpired(ttlMs): Iterates through requests, identifies any where Date.now() - req.createdAt >= ttlMs, deletes them from the Map, and returns the array of removed requests. 
addRequest(request) {
  const validTypes = ['play', 'pause', 'seek', 'change_video'];
  if (!validTypes.includes(request.type)) {
    throw new Error(`Invalid request type "${request.type}".`);
  }
  const id = request.id || randomUUID();
  const newRequest = {
    id,
    type: request.type,
    payload: request.payload ?? {},
    requesterId: request.requesterId,
    requesterName: request.requesterName,
    createdAt: typeof request.createdAt === 'number' ? request.createdAt : Date.now(),
  };
  this.pendingRequests.set(id, newRequest);
  return newRequest;
}

cleanExpired(ttlMs = 60000) {
  const now = Date.now();
  const removed = [];
  for (const [id, req] of this.pendingRequests) {
    if (now - req.createdAt >= ttlMs) {
      removed.push(req);
      this.pendingRequests.delete(id);
    }
  }
  return removed;
}
4. Key decisions & WHY
  • Map over Array for pendingRequests: Provides O(1) lookups and deletions by request ID when hosts approve or dismiss requests, avoiding O(N) linear scans.
  • Strict Action Type Whitelist: Restricting type to valid playback actions (play, pause, seek, change_video) prevents arbitrary strings from polluting server memory and crashing downstream approval handlers.
  • Passive TTL Sweep over Active Timers: Running cleanExpired(ttlMs) periodically or on-demand avoids allocating individual setTimeout handles for every incoming suggestion, saving Node.js event loop resources under high concurrency.
  • Decoupling Suggestions from State Mutation: Suggestions do not mutate room.playState or room.currentTime until explicitly approved by the host, maintaining strict server-authoritative state.
5. Alternatives not chosen & trade-offs
  • Storing pending requests in an array: Simpler syntax for listing, but deletion and lookup require O(N) filtering, which degrades performance as queue length grows.
  • Using Redis TTL keys: Adds external infrastructure complexity. For watch parties, keeping ephemeral requests in the room's in-memory Map is faster, zero-dependency, and automatically cleans up when the room is destroyed.
  • Active per-request setTimeout handles: If 100 requests arrive across 20 rooms, 100 separate timer handles would sit in the Node libuv timer queue. Batch scanning via cleanExpired is far more scalable.

  4. Calls room.cleanExpired() to prune stale requests, then counts active requests where requesterId === participant.userId. If >= 3, rejects with REQUEST_LIMIT_REACHED.

#onRequestAction({ socket, room, participant, data }) {
  const { type, payload: rawPayload } = data ?? {};
  const validTypes = ['play', 'pause', 'seek', 'change_video'];
  if (!type || !validTypes.includes(type)) {
    return emitError(socket, 'INVALID_REQUEST', 'Action type must be play, pause, seek, or change_video.');
  }

  // Validate payload per type
  let normalizedPayload = {};
  if (type === 'seek') {
    if (typeof rawPayload?.time !== 'number' || rawPayload.time < 0) {
      return emitError(socket, 'INVALID_REQUEST', 'Seek time must be a non-negative number.');
    }
    normalizedPayload = { time: rawPayload.time };
  } else if (type === 'change_video') {
    const videoId = extractVideoId(rawPayload?.videoId);
    if (!videoId) return emitError(socket, 'INVALID_VIDEO', 'Invalid YouTube URL or video ID.');
    normalizedPayload = { videoId };
  }

  // Enforce 3 pending requests per user
  room.cleanExpired();
  const userCount = room.getPendingList().filter((r) => r.requesterId === participant.userId).length;
  if (userCount >= 3) {
    return emitError(socket, 'REQUEST_LIMIT_REACHED', 'Limit of 3 pending requests per user reached.');
  }

  // Store and acknowledge
  const storedRequest = room.addRequest({ type, payload: normalizedPayload, requesterId: participant.userId, requesterName: participant.username });
  socket.emit('request_queued', { requestId: storedRequest.id });

  // Alert only HOST and MODERATOR sockets
  for (const p of room.participants.values()) {
    if (p.role === Role.HOST || p.role === Role.MODERATOR) {
      this.io.sockets?.sockets?.get?.(p.socketId)?.emit('action_requested', storedRequest);
    }
  }
}

3. How it works
When a host or moderator approves or rejects a request:
  1. withPermission('approve_request' / 'reject_request') verifies room membership and role authorization (only HOST or MODERATOR allowed; PARTICIPANT receives FORBIDDEN).
  2. Validates requestId exists and is stored in room.pendingRequests (otherwise returns REQUEST_NOT_FOUND).
  3. On Approval: Calls room.applyAction(request.type, request.payload) to mutate room state using the same logic as direct actions. Removes the pending request via room.removeRequest(requestId). #onApproveRequest({ socket, room, data }) {
  const { requestId } = data ?? {};
  if (!requestId) return emitError(socket, 'INVALID_REQUEST', 'requestId is required.');

  const request = room.getRequest(requestId);
  if (!request) return emitError(socket, 'REQUEST_NOT_FOUND', 'Request not found.');

  // Execute using shared Room action logic
  room.applyAction(request.type, request.payload);
  room.removeRequest(requestId);

  // Broadcast new synchronized state to everyone
  this.io.to(room.roomId).emit('sync_state', room.getState());

  // Notify hosts, moderators, and the requester
  this.#notifyRequestResolved(room, requestId, 'approved', request.requesterId);
}

#onRejectRequest({ socket, room, data }) {
  const { requestId } = data ?? {};
  if (!requestId) return emitError(socket, 'INVALID_REQUEST', 'requestId is required.');

  const request = room.getRequest(requestId);
  if (!request) return emitError(socket, 'REQUEST_NOT_FOUND', 'Request not found.');

  room.removeRequest(requestId);

  // Notify requester directly of rejection
  const requester = room.participants.get(request.requesterId);
  if (requester) {
    this.io.sockets?.sockets?.get?.(requester.socketId)?.emit('request_rejected', {
      requestId,
      reason: 'Rejected by moderator'
    });
  }

  // Notify hosts, moderators, and the requester of resolution
  this.#notifyRequestResolved(room, requestId, 'rejected', request.requesterId);
}

3. How it works
When a host or moderator approves or rejects a request:
  1. withPermission('approve_request' / 'reject_request') verifies room membership and role authorization (only HOST or MODERATOR allowed; PARTICIPANT receives FORBIDDEN).
  2. Validates requestId exists and is stored in room.pendingRequests (otherwise returns REQUEST_NOT_FOUND).
  3. On Approval: Calls room.applyAction(request.type, request.payload) to mutate room state using the same logic as direct actions. Removes the pending request via room.removeRequest(requestId). Broadcasts the updated room state to all room sockets via io.to(room.roomId).emit('sync_state', room.getState()).
  4. On Rejection: Removes the pending request via room.removeRequest(requestId). Finds the requester's socket (if connected) and emits request_rejected { requestId, reason } directly.
  5. In Both Cases: Calls #notifyRequestResolved(room, requestId, status, requesterId), which sends request_resolved { requestId, status } to every host and moderator socket, plus the original requester socket (deduplicating so no socket receives it twice). 
#onApproveRequest({ socket, room, data }) {
  const { requestId } = data ?? {};
  if (!requestId) return emitError(socket, 'INVALID_REQUEST', 'requestId is required.');

  const request = room.getRequest(requestId);
  if (!request) return emitError(socket, 'REQUEST_NOT_FOUND', 'Request not found.');

  // Execute using shared Room action logic
  room.applyAction(request.type, request.payload);
  room.removeRequest(requestId);

  // Broadcast new synchronized state to everyone
  this.io.to(room.roomId).emit('sync_state', room.getState());

  // Notify hosts, moderators, and the requester
  this.#notifyRequestResolved(room, requestId, 'approved', request.requesterId);
}

#onRejectRequest({ socket, room, data }) {
  const { requestId } = data ?? {};
  if (!requestId) return emitError(socket, 'INVALID_REQUEST', 'requestId is required.');

  const request = room.getRequest(requestId);
  if (!request) return emitError(socket, 'REQUEST_NOT_FOUND', 'Request not found.');

  room.removeRequest(requestId);

  // Notify requester directly of rejection
  const requester = room.participants.get(request.requesterId);
  if (requester) {
    this.io.sockets?.sockets?.get?.(requester.socketId)?.emit('request_rejected', {
      requestId,
      reason: 'Rejected by moderator'
    });
  }

  // Notify hosts, moderators, and the requester of resolution
  this.#notifyRequestResolved(room, requestId, 'rejected', request.requesterId);
}

4. Key Decisions & Why

  • Why keep live state in-memory and only persist metadata to MongoDB? High-frequency video sync (sub-second seek calculations, playback toggles) requires zero latency ($< 1\text{ ms}$). Round-tripping ephemeral play state to a remote database introduces 50–200ms network lag and write bottlenecks. The in-memory Room class remains the authoritative source of truth, while MongoDB stores only restart-surviving state.
  • Why fire-and-forget writes? A slow database write or network hiccup must never stall a user's WebSocket message. By not awaiting write operations inside event handlers, real-time broadcasts continue without pause.
  • Why maxTimeMS: 3000? If MongoDB experiences heavy load, operations fail fast after 3 seconds instead of hanging promises indefinitely and leaking server memory.
  • Why 7-day TTL indexes? Rooms and chat logs for ephemeral watch parties have finite lifetimes. Leveraging MongoDB's background TTL index thread automates garbage collection without external cron workers.

5. Alternatives Considered

  • Alternative: Awaiting database writes in socket handlers: Guarantees write confirmation before broadcasting, but ties WebSocket responsiveness directly to database latency. A database slowdown would freeze video controls and chat for all connected users.
  • Alternative: Restoring all rooms at boot: Scanning and restoring thousands of dormant rooms at server startup consumes unneeded RAM. Lazy restoration on join_room restores only rooms that users actually visit.

6. Problems Encountered & Fixes

  • Problem: Database failure crashing socket handlers: Uncaught promise rejections in Mongoose queries could crash the Node.js process. Fix: All repository write calls chain .catch() to log warnings, and findRoom / getRecentMessages wrap operations in try/catch returning safe fallback values (null or []).

4. Key Decisions & Why

  • Why better-sqlite3 over sqlite3? better-sqlite3 executes operations synchronously directly against native SQLite C bindings. Unlike asynchronous drivers that require Promises and tick through the libuv threadpool for every tiny query, synchronous execution simplifies initialization and transaction flow with dramatically higher performance ($> 50,000$ queries/sec).
  • Why store rooms as empty on restoration? Ephemeral WebSocket connections (TCP sockets) cannot survive a server process restart. Storing disconnected socket objects in a database causes corrupted state. Restoring rooms as empty, dormant containers preserves room codes and video queues while allowing real people to reconnect cleanly.
  • Why designate the first joiner as Host? If a room was restored without occupants, the original host is not connected. If the first joiner were a standard participant, the room would be locked with no host capable of playing or managing controls. Making the first joiner Host ensures the room is immediately usable.

5. Alternatives Considered

  • Alternative: PostgreSQL or Redis: Excellent for multi-server distributed scaling, but introduces external infrastructure dependencies (Docker, networking, credentials) for local development. SQLite embedded in a local .db file provides zero-configuration persistence that works out-of-the-box.
  • Alternative: JSON file serialization (fs.writeFileSync): Prone to race conditions and corruption during abrupt process termination. SQLite provides ACID guarantees with write-ahead logging (WAL), preventing partial writes.

6. Problems Encountered & Fixes

  • Problem: Pruning empty rooms while restored: deleteIfEmpty in RoomManager could prematurely delete restored rooms before anyone has a chance to join. Fix: Restored rooms are flagged with isRestored = true and retained until active session conclusion.

7. Expected Interview Questions & Answers

Q1: Why is synchronous SQLite via better-sqlite3 acceptable in an asynchronous Node.js server?
In SQLite, queries against local disk or in-memory databases take microseconds ($< 0.1\text{ ms}$). The overhead of wrapping operations in asynchronous callbacks, Promise allocations, and libuv threadpool context switching frequently takes longer than the SQLite query itself. Because room creations and video updates occur at human interaction frequencies (once every several minutes per room), synchronous execution introduces virtually zero event loop latency while eliminating asynchronous race conditions.
Q2: How does the server handle room ownership when restoring rooms after a server restart?
All socket connections are severed during a restart, meaning no original hosts exist. When the server reconstitutes rooms into memory, they are initialized with zero participants. In MessageHandler.#onJoinRoom, the server evaluates isFirstJoiner = room.isEmpty(). If true, the incoming user is granted Role.HOST, receives full administrative authority, and starts the request sweeper timer. Subsequent joiners become standard Role.PARTICIPANT.
Q3: Why make database persistence toggleable via an environment variable?
During automated test suites and high-throughput unit testing, maintaining database files introduces disk I/O, file locks, and state pollution across runs. A feature flag (PERSIST_ROOMS=true) allows automated tests and stateless deployments to run entirely in ephemeral memory, while production environments can enable persistent storage with a single configuration flag.
